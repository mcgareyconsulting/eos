# P5 — rules notes (notification core)

P5 does not edit `firestore.rules`. Every P5 write goes through server
actions (Admin SDK), which bypass rules. The rules below close the client
paths a hand-rolled client could still use. Apply them in the rules package.

## 1. `notifications/{id}` — no change

Rows are now pointer-only (`user_id, team_id, entity_type, entity_id, kind,
event, actor_id, created_at, read_at, archived_at`). The current rule is
still correct:

```
match /notifications/{id} {
  allow read:  if authed() && resource.data.user_id == request.auth.uid;
  allow write: if false;
}
```

Legacy rows still carry `entity_title`, `detail`, `team_name` and
`actor_name`. The app ignores them. The owner of the row can still read
them with the client SDK. To remove that leak, run a one-time backfill that
deletes those four fields (spec §8 migration; script not in P5).

## 2. Follow fields are server-only

`follower_ids` and `assigned_by` decide who is a locked follower and who is
told. Today members can write `issues`, `rocks`, `scorecard_metrics` and
`headlines` from the client, so a client could remove a locked follower or
make itself the assigner. Add this guard to the client `update` rule of
`todos`, `issues`, `rocks`, `scorecard_metrics` and `headlines`:

```
function touchesFollowFields() {
  return request.resource.data.diff(resource.data).affectedKeys()
           .hasAny(['follower_ids', 'assigned_by']);
}
// … allow update: if <existing condition> && !touchesFollowFields();
```

And to client `create` on the same collections:

```
// … allow create: if <existing condition>
//   && (!('assigned_by' in request.resource.data)
//       || request.resource.data.assigned_by == request.auth.uid)
//   && (!('follower_ids' in request.resource.data)
//       || request.resource.data.follower_ids.size() <= 1);
```

(`admin()` keeps its existing bypass only if admins also edit through the
client; prefer applying the guard to admins too.)

## 3. `entity_activity` / `entity_comments` — no change

`purgeItem` deletes these with the Admin SDK. The existing read rules stay.

## 4. Indexes

`purgeItem` queries `entity_comments`, `notifications` and
`entity_activity` with one equality filter (`entity_id ==`) each, and
filters `entity_type` in code. `loadViewers` queries `team_members` with
`user_id in [...]`. Single-field indexes cover all of them. No composite
index is needed.
