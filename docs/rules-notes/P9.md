# P9 — firestore.rules needed for threads

P9 did not edit `firestore.rules`. Every comment write goes through the Admin
SDK behind `lib/firebase/thread-gate.ts` (`requireThreadAccess` → the item's
`accessFor(type).canComment`), and `entity_comments` writes stay
`allow write: if false`. What needs rules is the **client read** of a thread
(the live listener in `components/entity-comments.tsx`).

## The problem

`entity_comments` reads are team-gated today (`isMember(resource.data.team_id)`
or admin). A thread is filed under the **item's own team**, so:

- an off-team to-do assignee (D1) reads an empty thread,
- a rock's audience (teams and persons) reads an empty thread (the rock query
  is already by entity alone, so it is refused outright for them),
- a milestone assignee outside the rock's full set reads nothing,
- a private to-do's creator and assignee, who need not be on the team, read
  nothing,
- headline threads (`entity_type == "headline"`) are new.

Thread reads must become **item-aware**: a comment is readable by whoever can
`canSee` the item it hangs off (spec §5.1: "A person can read and write in
the thread only if they can see the item"; access decreasing decreases thread
access, old comments included).

## Queries the client now runs

| Thread | Query | Note |
|---|---|---|
| issue | `entity_comments where team_id == T and entity_type == "issue" and entity_id == X` | unchanged shape |
| headline | `... entity_type == "headline" ...` same shape | new type |
| rock | `entity_comments where entity_type == "rock" and entity_id == X` | no `team_id` clause (as before) |
| to-do / milestone | `entity_comments where entity_type == "todo" and entity_id == X` | **changed**: dropped `team_id`; the thread is filed under the item's team, not the page's, so an off-team assignee's page team never matched |

Because to-do and rock queries carry no `team_id`, a rule cannot lean on a
query constraint; it must look the parent up with `get()` /
`exists()` on `resource.data.entity_id`. Until the rule ships, those two
queries are refused for everyone and `useCollection` keeps only the server's
first paint (it logs the refusal) — so ship the rule with, or before, this
branch reaches users. (If that ordering is a problem, restore the
`team_id == T` clause on the to-do query as a stopgap; off-team assignees
then see an empty thread, as today.)

## Rules text (sketch)

```
// Parent lookups by thread type. `d` is the entity_comments row.
function threadParent(d) {
  return d.entity_type == 'rock'     ? get(/databases/$(database)/documents/rocks/$(d.entity_id)).data
       : d.entity_type == 'issue'    ? get(/databases/$(database)/documents/issues/$(d.entity_id)).data
       : d.entity_type == 'headline' ? get(/databases/$(database)/documents/headlines/$(d.entity_id)).data
       :                               get(/databases/$(database)/documents/todos/$(d.entity_id)).data;
}

match /entity_comments/{id} {
  allow read: if isAdmin() || canSeeThreadItem(resource.data);
  allow write: if false;
}
```

`canSeeThreadItem(d)` mirrors `lib/access`:

- **issue / headline**: `isMember(parent.team_id)` (admin covered above).
- **rock**: parent team member, member of a team in
  `audience_team_ids` (legacy `shared_team_ids` until P13), or
  `request.auth.uid in audience_user_ids`; a Private rock
  (`private == true`, legacy `team_only`) has no audience.
- **to-do** (`entity_type == "todo"`, parent has no `source_rock_id`): team
  to-do → `isMember(team_id) || owner_id == uid`; private
  (`visibility == "private"`) → `created_by == uid || owner_id == uid`
  (members and leaders excluded).
- **milestone** (`entity_type == "todo"`, parent has `source_rock_id`): the
  rock rule on the parent rock (`get(rocks/$(source_rock_id))`) or
  `owner_id == uid`.

Do not rely on the comment's own `team_id` for anything but the issue and
headline queries; for the other types it is only the filing team.

## Other client reads this touches

- None new. `entity-comments.tsx` calls two server actions
  (`loadThreadInfo`, `loadCommentAuthorNames`) that use the Admin SDK.
- `entity_activity` (the to-do trace) has the same off-team gap as before
  (see `P8a.md`, P11).

## Deep links

`?rock=`, `?milestone=`, `?issue=`, `?headline=` open the item client-side
from the page data the viewer already has. No rules involved; a link to an
item the viewer cannot see opens nothing (the server page does not list it).
